# email-rag GitHub 开源发布实施计划与执行记录（2026-10-11）

> 本文档记录 email-rag 首次公开发布的准备工作：隐私审计、历史净化、许可与 CI 补齐、README 发布态改造，以及发布清单。执行采用"发布副本"模式——所有清洗与改造在独立的发布副本中进行，本地开发仓库保持零改动。

## 背景与原则

- 发布前审计发现三类需要处理的内容：历史提交中测试夹具使用的内网地址、提交作者身份与发布身份不一致、README 中与实现不完全一致的附件表述。
- 处理原则：
  1. 所有改造在发布副本（`email-rag-publish`）中进行，不触碰本地开发仓库；
  2. 原始邮件数据（数据库、导出目录、审计报告）从不进入版本库；
  3. 用工具而不是人工检查来兜底——CI 内置泄漏护栏。

## 完成内容

### 1. 发布副本与历史净化

- `git clone` 本地仓库到独立发布副本；
- `git filter-repo --replace-text`：将历史中测试夹具的内网地址替换为 RFC 5737 文档保留地址（`192.0.2.0/24` 段）；
- `git filter-repo --mailmap`：将全部历史提交的作者/提交者统一为发布身份；
- 净化后 37 条提交叙事完整保留，全部提交作者为统一发布身份。

### 2. 许可与打包元数据

- 新增 `LICENSE`（Apache-2.0 官方正文）；
- `pyproject.toml`：PEP 639 SPDX 许可表达式（要求 `setuptools>=77`）、作者、关键词、分类器、项目 URL；`dev` 依赖补充 `pytest-cov`（README 此前已教用户使用覆盖率命令，但依赖里缺它）。

### 3. CI：测试 + 泄漏护栏（`.github/workflows/test.yml`）

- `test` 任务：Python 3.10 / 3.11 / 3.12 矩阵，安装、跑 115 个测试并输出覆盖率；
- `leak-guard` 任务（隐私护栏，防止回归）：
  - `.env` 不得进入版本库；
  - 全仓库扫描内网地址（192.168.x.x）；
  - 扫描常见密钥字面量模式（sk-/ghp_/tvly- 等）。

### 4. README 发布态

- 顶部 badge（CI + 许可）；
- 新增"它解决什么问题""特性""贡献指南""许可与免责"四个章节；
- 校准附件表述：本工具不解析、不导出附件；原始邮件（含附件字节）完整保存在本地 SQLite——修正了此前"不下载附件"的不准确说法。

## 发布清单（发布日执行）

1. 在 GitHub 创建空仓库 `email-rag`（public；不勾选自动生成 README/.gitignore/LICENSE）；
2. 在发布副本中执行：`git remote add origin https://github.com/<你的用户名>/email-rag.git`；
3. `git push -u origin main`（首次推送由 Git Credential Manager 浏览器授权）；
4. 建议在仓库设置中补充描述与 topics：`email`、`imap`、`deduplication`、`rag`、`local-first`、`markdown`；
5. 确认 CI 首次运行通过（Actions 页）。

## 后续同步约定

- 本地开发仓库与发布副本相互独立：新功能继续在本地开发，发布时把增量改动同步到发布副本，再推送；
- 禁止把本地 `.env`、`data/`、`output/`、`.superpowers/` 复制进发布副本；
- 若发布副本内新增提交，保持作者身份与发布身份一致（副本已配置好仓库级 `user.name` / `user.email`）。
